43 TOTP — a genuinely new interaction, not just a new op

RFC 6238 is HMAC over a moving time counter — the toolkit's existing crypto primitives, no new algorithm to design around. What's actually new is the output: every op in this file so far computes once and sits still; a TOTP code is correct for exactly 30 seconds and then silently wrong, which is a value that ticks on a clock rather than on an event (30c's recv appends on an external message; this changes on its own with nobody doing anything). 43a the two ops. 43b the ticking output row. 43c where it plugs into 42d's QR work. 43d where the secret itself lives.

43a totp.generate / totp.verify — a pair, like sign/verify already is
Same shape the toolkit already uses for asymmetric pairs: one op produces, one op checks. generate takes a base32 secret plus the standard period/digits/algorithm params (defaults match every authenticator app: 30s, 6 digits, SHA-1) and outputs the current code. verify takes a secret and a candidate code, returns bool — same as verify/gpg.verify already do for signatures.

SHA-1 is the default specifically because it's what every real authenticator app (Google/Microsoft/Authy) actually ships — SHA-256/512 are real RFC options but choosing them makes the secret incompatible with anything but Basilisk itself, so the param exists but shouldn't be the first thing a user sees. verify's ±1-step window absorbs ordinary clock drift between two devices, matching how every real TOTP verifier behaves.

Every other OutputList row is a snapshot of the moment the cell ran. A TOTP row is the one place staleness is the entire point — the countdown ring isn't decoration, it's the difference between "this code still works" and "this code is already wrong."
