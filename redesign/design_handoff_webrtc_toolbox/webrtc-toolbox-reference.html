Four things close out the design pass. 30a what's a device preference (localStorage) vs. what needs real storage (IndexedDB) — including a fact worth designing around: an RTCCertificate can be structured-cloned into IndexedDB and reused across sessions, which is the only way 29a's "Pin across sessions" can actually work. 30b the IndexedDB schema itself. 30c is the real gap: quorum.recv doesn't produce one output, it produces a stream of them over time, and turn 21a never addressed that. 30d closes the three ⬜ items WEBRTC-TOOLBOX.md still listed as undesigned.

29 What else fits — identity, reliability, mesh, and bandwidth

Sweeping the rest of the WebRTC reference against Basilisk's actual shape (a crypto/text notebook, not a calling app) rules out most of what's left: media capture, DTMF telephony, and encoded transforms have no user here and stay unplanned (WEBRTC-TOOLBOX.md §4/5/7). Four things are a real fit, though — one of them, 29c, ties directly into a toolkit primitive that already exists (sss.split/combine) and is the strongest new idea this pass found.

29a a certificate/identity op for the DTLS fingerprint 28b already displays but nothing yet produces. 29b data-channel reliability as a param block, not a hidden default. 29c a mesh session — Quorum's name already implies more than two parties; this is what makes that literal, wired straight to k-of-n secret sharing. 29d the live bandwidth/quality strip §6 left as a placeholder.

28 The full handshake, made visible — session log, peer detail, and what a "hexdump" honestly can be

24c's debug console was a stub. A real session log has to cover the whole handshake, which has more stages than turns 21a–26 modeled explicitly: signaling (offer/answer exchanged over whatever out-of-band channel Quorum uses — the PGP-signed invite blob) → ICE (gathering, trickling, pair checks — 23a/23b/26a/26b) → DTLS handshake (once ICE picks a pair, the two peers do a DTLS handshake to secure the channel — new to this design) → SCTP association (the data-channel transport negotiates on top of DTLS before any channel can open — also new) → data channel open → message flow → close. 28a is that full log. 28b is the peer detail this log's rows link into — IP/port/candidate-pair/transport specifics. 28c is the honest version of "packet hexdump": RTCDataChannel only ever gives JS the decrypted message payload, never a raw wire capture, so this shows the message's bytes, not a sniffed packet — the design has to say that plainly rather than imply something WebRTC can't do. 28d ties all five phases back to which existing turn/component owns each one.

26 Deep-dive corrections from MDN's connectivity & session-lifetime guides

Reading MDN's WebRTC connectivity and Session lifetime guides in full surfaces things turns 23–25 got wrong or left out: a fourth UDP candidate type (prflx), the controlling/controlled agent split that decides who nominates a pair, ICE restart as the real recovery path when a connection fails (not just "Configure TURN"), and the pending/current local-remote description split. 26a corrects 23a/23b's candidate types, 26b adds the controlling/controlled role, 26c adds ICE restart as a SessionStrip action.

26a Correction — 23a was missing prflx, and TCP candidates are a real (rare) fourth column
MDN lists four UDP candidate types, not three: host, prflx (peer reflexive — discovered mid-negotiation via trickle ICE, not requested upfront like srflx), srflx, relay. 23a's list skipped prflx entirely. TCP candidates exist too (active/passive/so) but are rare enough in practice that they get a protocol badge, not their own row type — same visual treatment as any UDP row, just tagged tcp instead of udp.

prflx rows can appear after gathering already "finished" (trickle ICE keeps discovering candidates during negotiation) — the OutputList for 23a needs to append rows live, not just render a static list from one gather pass.
26b Controlling vs. controlled agent — one badge on the matrix, not a user decision
ICE picks one peer as the controlling agent, who makes the final call on which candidate pair wins and tells the other (controlled) peer. This is assigned by the protocol, not chosen by the user — the UI's only job is to say which role this peer has, so "why did it pick that pair and not this faster one" has an answer. 26c ICE restart — the real recovery action, distinct from "Configure TURN" (22b)
22b's "Configure TURN" fixes a server-config problem discovered before connecting. ICE restart is different: it recovers a session that connected fine and then broke (network switch, congestion) — MDN's fix pattern is setConfiguration() + restartIce() on iceConnectionState === 'failed', with media/data continuing on the old path until the new one is ready. SessionStrip (21a) needs this as a distinct action, not folded into Cancel.

Clicking it doesn't reopen the caret or touch the recipe — it calls restartIce() on the existing QuorumSession, same live sessionHandle (21a), and the strip returns to connected automatically once the new path is up. This is the item turn 22's two-peer verification checklist should specifically test: does data actually keep flowing on the old path while restart negotiates the new one, per MDN's behavior.

23 WebRTC toolbox, ground up — starting with ICE & STUN

Turns 21a/22b treated Quorum's WebRTC plumbing (rtc.ice, stun.check) as two supporting ops behind a session feature. 22a ParamField — a "secret" param can't become free text or serialize into a share link
Decision: the registry marks certain params secret: true (quorum.offer/join key=, rtc.ice credential=). Sharing the recipe link omits the field's value entirely; the recipient sees the same locked, unbound state and must bind their own.

21d Nested-caret fit — its own slot filter, not the cell's
Decision: a compound op declares nestSlots in the registry, one entry per internal slot with its own expected kind. The nested caret (20f) reads that slot's kind, not the cell's overall tip — today it's reusing the cell tip's fit set, which is wrong whenever a slot's kind differs from the cell's edges (e.g. the sign slot inside sign+encrypt wants bytes→signature, not bytes→ciphertext).
