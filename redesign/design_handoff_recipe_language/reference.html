48 Auditing the WebRTC/Types work (21-31) against the real grammar

Same exercise 47 just did for tee/foreach, applied backward to the earlier WebRTC toolbox and Types work — now that docs/RECIPE.md and the real type-registry.js are both actually read. One real naming bug, one design that should reuse an existing idiom instead of inventing a parallel one, and one piece of good news worth stating plainly rather than re-litigating.

48b quorum.recv already has a real-language answer: bundle + foreach
Turn 30c invented a bespoke fix for "an op that produces many values over time" — cell.output becomes an array, plus a new collect-vs-run-downstream toggle. But the language already solves exactly this shape: foreach's tip is a bundle of per-item tips, explicitly "do not pipe the bundle into cipher/KDF ops; use @slots written in the body." Multiple messages arriving over a session is structurally the same problem sss.split's shares already are.

30c's actual UI observation (a live-appending list, defaulting to inert rather than auto-cascading) is still correct and still needed — what's wrong is inventing a new cell.output shape and a bespoke mode toggle when foreach over a live-appending source already models "one op, many results over iterations" as a first-class bundle. The retrofit target becomes: does foreach's body support a live, still-growing source (a data channel) rather than only a pre-computed one (shares)? That's a real, narrower question for whoever owns the engine — smaller than 30c's original ask.
48c quorum.mesh's MESH region may not need to exist

RECIPE.md's own real example for shares is a plain foreach body — the same mechanism might just work as-is, no new region: sss.split | blip39 | foreach - quorum.offer | send, one iteration per share, using the SESSION region (21a) already built per-cell rather than a new roster widget.

This isn't a confident retraction the way 48a/47d are — RECIPE.md never shows a body step that blocks waiting for a network peer, only ever synchronous per-item transforms. If foreach's execution model can't pause per-iteration for quorum.offer's waiting-peer state (21a), then 29c's dedicated MESH region is the right call after all — the UI as designed doesn't need to change either way, this is purely a question for whoever implements whether the roster UI is load-bearing or removable in favor of an existing idiom.
48d The good news: the network type system was already right
Worth stating plainly rather than re-auditing what already passed: the real type-registry.js (read for turn 32) already declares host, endpoint, candidate, sdp, certificate, session, channel, peer, connstate, stats as its own dedicated "Network types" section — nearly a one-to-one match with what turns 23-30 speculated into existence before that file was ever read. The 31/32 int-literal widget's 0x/0b/0o support also matches the real parseIntLiteral exactly — no correction needed there despite RECIPE.md's own stem-literal grammar only mentioning decimal/hex, because the widget serializes through a lit step rather than emitting a bare EBNF literal token, so the two aren't in conflict.
Net result of this audit
1 real bug (48a, mechanical rename)
2 open questions for the engine owner (48b, 48c)
1 confirmation nothing needs fixing (48d)
The pattern worth carrying forward: reading the actual grammar/registry caught one real naming defect and surfaced two places where a bespoke UI mechanism might collapse into an idiom the language already has — smaller, cheaper fixes than a full redesign, and exactly the kind of finding that's only available by reading the source rather than continuing to design from the type system's shape alone.
46 tee and foreach — the real ambiguity is two gaps with the same label

Read the real RecipeChipFlow.tsx to ground this rather than guess. The nest infrastructure already exists — ChipStemView.hasNest/branches/body render an indented - line below the stem row exactly like docs/RECIPE.md's own syntax. The actual bug is narrower and confirms the hunch: the gap immediately after a stem chip on its own row ("continue the main chain") and the gap inside its nested branch/body row ("build the subchain") render as the literal same component with the literal same label — InsertGap label="Insert step here", or "Insert first step" when empty, in both places. Nothing in the chip, the gap, or the layout tells a user which one they're looking at. foreach has it worse, confirmed in 46c: its body has no selector chip at all, just a bare dash — even less to anchor on than tee's :public-style branch chip.

Worse: nothing about tee's own chip marks it as a container. It renders through the exact same SuggestChip variant="placed" as base64 or genkey — a linear, one-in-one-out op — so there's no signal at the chip itself that "what comes next" is a different kind of question for this one.
46b Three small fixes, no new components
Nothing here needs a new widget — InsertGap, SuggestChip, and the existing indent-line layout already carry everything needed. It's a props/copy fix plus one auto-focus behavior on insert.
tee splits into branches ↓
- :public + step in :public
"Insert after tee" only appears once this branch has ≥1 step
The three changes
1. gap label: `+ step in ${branchSelector}`
2. onCaretInsert('tee') → auto-set activeGap
  to the new branch's first body slot
3. hide the stem-row gap until hasNest body ≥1
(1) is the real fix — a branch gap's label names the branch it belongs to, so it can never be mistaken for the top-level one. (2) means the caret that just inserted tee immediately hands off to the branch's own empty gap — activeGap already exists as a prop, this is just choosing where it points on insert instead of leaving it null. (3) removes the confusing gap entirely for the one moment it has nothing valid to mean yet — tee with an empty branch can't meaningfully continue past itself, so don't show a gap that implies it can.
46c foreach confirmed worse — its body has no selector chip to anchor on
The bet was right. ChipStemView.body (the unbranched-nest path, exactly foreach's shape) renders the same indented - line as a branch but with no SuggestChip variant="selector" in front of it — tee at least has :public to look at; foreach's indent starts with nothing but the dash itself.

Not a new prop shape — stem.body's render branch in RecipeChipFlow.tsx just needs the same leading chip ChipRow for branches already gets, using a fixed label instead of a per-branch selector string (since a loop body has exactly one, unnamed). Same 46b fixes apply identically: the gap says "+ step in loop body," and inserting foreach auto-focuses that gap instead of leaving the stem-row gap active.
