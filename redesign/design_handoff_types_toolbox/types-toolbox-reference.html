31 Types as instantiable toolbox entries, and docstring links

This one is toolkit-wide, not WebRTC-specific — it changes how the Input / output category works everywhere. Today "input" is one generic text box, and getting a typed value (an int, a keypair) means input → cast op. The alternative: a Types category where each type is its own source op with a widget shaped like that type's native form — an int field takes 42 or 0x2A directly, no parse step; a keypair can be generated or imported as a first-class origin, not just genkey's output. 31a the category. 31b the Int/Hex widget. 31c KeyPair as an instantiable type, not only a generate-op result. 31d every tool card gets a docs link back to the real spec/MDN page it wraps.

31a "Input / output" becomes "Types" — instantiate, don't cast
18b's shelf listed a flat "Input / output" category, 7 ops, generic gray dot — really just "give me some bytes/text from somewhere." Splitting it into one entry per real kind lets each carry its own native widget instead of a text box plus a cast step downstream. Text stays (it is what free text should be), but Int, Hex, KeyPair, and Certificate get their own shape.

Registry — types are ops with no inputs
op.kind: 'type' // vs 'transform' | 'source'
op.instantiates: OpKind // which kind it produces
Nothing about downstream fit-checking (19a/20b/25d) changes — a type op's output kind flows through the caret exactly like genkey's already does. This is a shelf/authoring reorganization, not a new pipeline mechanism. Existing recipes using the old input :text shape keep working — it just now reads as text from the Types category instead of a generic "Input / output" one.
31b Int — one field, decimal or 0x hex, no parse step to add
Today, getting the number 42 into a pipeline means input :text → some parse-int op the toolkit may not even have yet. The Int type widget accepts either notation directly and normalizes on blur, showing both forms plus the byte length it'll serialize to — so what you typed and what the pipeline actually holds are never in question.

0x2A
= 42 decimal·1 byte·big-endian
Widget contract
op: types.int
accepts: /^-?\d+$/ | /^0x[0-9a-f]+$/i
out: IntValue { value: bigint, byteLength }
hex is the sibling widget for the reverse case — a byte string the user thinks of as hex first (a key, a nonce), where int is a small number they think of as a number. Both normalize to the same underlying bytes kind on output, so an op downstream that wants bytes doesn't care which type widget produced them.
31c KeyPair — generate or import, same type either way
genkey (18b, WebCrypto category) stays exactly as it is — it's still how most keypairs get made. But a keypair a user already has (exported from another tool, a long-lived identity) had no way to enter the pipeline as a typed value before; it had to masquerade as base64 text and get parsed. The Types entry offers both origins behind one segmented control, so the rest of the pipeline sees the same CryptoKeyPair kind regardless of where it came from.
keyPair
Generate Import
Paste JWK or PEM…
Private half stays non-extractable once imported, same as a generated key
Widget contract
op: types.keyPair
mode: 'generate' | 'import'
generate: delegates to genkey's own param set
import: accepts jwk | pkcs8+spki pem
"Generate" mode isn't a second implementation — it renders genkey's exact param form inline and produces the identical output shape, so a recipe can be authored either from Types or from WebCrypto and behave the same. This is the template for any future type that has both a "make one" and "bring your own" origin — certificate (29a) is the next candidate: generate ephemeral vs. import a pinned one.
31d Every tool card links back to the real spec it wraps
One line, bottom of the inline param editor (18b's pattern) and the caret's hover/detail card alike — a quiet "Docs ↗" pointing at the actual MDN or spec page the op is a thin wrapper over. Doesn't compete with the op's own description text; it's a footer, not a callout.
genkey Generate a WebCrypto keypair
ec/p256 · non-extractable private half
↗ SubtleCrypto.generateKey — MDN
quorum.offer Open a WebRTC session, wait for a peer
↗ RTCPeerConnection — MDN
Registry — one field, every op
op.docUrl?: string
Optional, so ops with no single canonical spec page (composite ops like openpgp.signAndEncrypt) simply omit the footer rather than linking somewhere approximate. Populate it once per op at registry-authoring time — genkey→SubtleCrypto.generateKey, rtc.ice→RTCConfiguration.iceServers, rtc.gatherCandidates→RTCIceCandidate, aes.encrypt→SubtleCrypto.encrypt — this is documentation-authoring work, not a design decision per op.
